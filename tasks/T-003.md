## Goal

Commit to a target architecture for the web port and write it down, so the porting tasks
stop being speculative.

## Acceptance Criteria

- [x] ADR records the decision on each axis:
  - [x] Language and build tooling
  - [x] UI approach (DOM/CSS vs canvas vs hybrid) — see the note below
  - [x] Board rendering (WebGL vs Canvas2D vs CSS 3D transform)
  - [x] Where the FFG importer runs (outcome of T-002)
  - [x] Texture storage format (outcome of T-001)
  - [x] Persistence (OPFS vs IndexedDB, and the split between them)
  - [x] Whether any server component exists at all
- [x] Explicitly records the rejected alternatives, including the Unity WebGL build, with reasons
- [x] Records the content licensing constraint and what it forbids
- [ ] Reviewed and agreed before T-004 starts

## Notes

**Dependency on T-001/T-002 removed on 2026-08-25.** Both are blocked on
licensed FFG files nobody here has. Keeping the ADR blocked behind them would
have left every remaining decision unrecorded indefinitely, including the ones
that gate T-016 and have nothing to do with the importer. The two axes that
genuinely need those outcomes — texture storage format, and whether a browser
can reach the installed app files — are recorded as blocked with the
constraints and a recommendation, not silently decided.


Baseline recommendation going in, to be challenged rather than assumed:

- TypeScript SPA shipped as a PWA. One artifact replaces all four current build targets
  (Windows, Mac, Linux, Android).
- DOM/CSS for menus, editor and dialogs; WebGL or Canvas2D for the board only. The current
  "tilted board canvas" is a perspective transform, which CSS 3D handles natively.
- No server for normal operation. Content packs already come from
  `raw.githubusercontent.com/NPBruce/valkyrie-store` (`RemoteContentPackManager.cs:65,70`),
  which `fetch()` reaches directly.
- Node earns its place in tooling and possibly the importer, not in hosting.

Hard constraint: imported FFG content is copyrighted and must never be served from our origin.
It stays client-side. That means hundreds of MB per user in OPFS, and rules out any thin-client
design that streams assets from a server.

Also worth deciding here: whether the web port replaces the Unity app or ships alongside it.
That changes how much the two need to agree on save format.

**The baseline recommendation in this task's notes turned out to be wrong, and
that is the most useful finding.** The notes describe the board as a "tilted
board canvas" whose perspective transform CSS 3D would handle natively. Checked
against the scene: `Game.unity` sets the camera to `orthographic: 0` with a 60
degree field of view, but `m_LocalRotation` is identity and
`CameraController.cs` contains no rotation code at all — it pans in x/y and
zooms in z. A perspective camera pointed head-on at a plane is visually
identical to an orthographic one. **There is no tilt**; the board is a flat
pan-and-zoom 2D scene. That removes the reason to reach for CSS 3D or WebGL,
and the recommendation is Canvas2D.
