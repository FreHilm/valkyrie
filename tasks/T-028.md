## Goal

Apply `highlight`, which marks the board space an event points at. Parsed onto
`QuestEvent` and never read.

## Acceptance Criteria

- [x] An event with `highlight` marks its location on the board
- [x] A highlight event draws no item card in its dialog — `DialogWindow.cs:211` returns early
- [x] The mark is cleared the way `TokenBoard` clears it
- [x] Verified in a browser on a scenario that uses it

## Notes

Used by 5 MoM scenarios: 2230h At The Bird's Pet Shop, In Places Unseen, The
Fall of House Lynch, The Robbery of the Kadakian Idol, and The Truth — 48 uses
in total, so it is how those scenarios direct attention, not a decoration.

`EventManager.cs:278` calls `tokenBoard.AddHighlight(e.qEvent)`.

## Progress

- 2026-08-28: Found while auditing the play loop against the C#.

- 2026-08-28: `AddHighlight` has two branches, and implementing only one would
  have been incoherent, so both are here: an event that hands over exactly one
  resolved `QItem` draws that card where it points, and anything else draws a
  marker. `DialogWindow.DrawItem` is the other side of the same question — the
  same card, beside the dialog, when the event is *not* a highlight — and it
  was also unimplemented, so the guard at `DialogWindow.cs:211` had nothing to
  guard.

  Two real bugs surfaced while verifying, both silent:

  - A canvas `fillStyle` is not a stylesheet. Handed `var(--x, #fff)` it keeps
    what it had — opaque black — and does not throw. So the marker painted
    black on a near-black board and read as nothing having been drawn. This
    already affected monsters with no art, which have been drawing as black
    squares rather than red since the board landed. Now resolved through
    `resolveColour`, with both tints defined as real custom properties.
  - The draw loop iterated a hand-written `[TILE, TOKEN, MONSTER]`, so the new
    `HIGHLIGHT` layer was built into the scene and never painted. The order is
    now derived from `Layer`, with a test that it covers every value.

  Verified in Chrome on a scratch scenario with all three cases: the marker
  paints `#eab30899` at the space, the Brass Key's own card draws there when
  the event hands one over, and the same card appears beside the dialog when
  the event is not a highlight — never both. The card landing at screen centre
  is correct, not a placement bug: `EventManager` aims the camera at the
  event's location, so the space it points at is the space you are looking at.
