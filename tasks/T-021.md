## Goal

Package the web port as an installable, offline-capable PWA. This is what lets one artifact
replace all four current build targets: Windows, Mac, Linux and Android.

## Acceptance Criteria

- [ ] Installable on desktop and Android, with correct name, icons and splash
- [ ] Fully functional offline once content is imported — no network needed to play
- [x] Service worker caching strategy that updates the app without destroying user content
- [x] `navigator.storage.persist()` requested, with a clear explanation to the user of why
- [x] Storage usage surfaced in the UI, with a way to remove content packs and reclaim space
- [x] Update flow that tells the user a new version is available rather than swapping under them
- [ ] Verified on the browser matrix agreed in T-003

## Notes

**Dependency on T-018 removed on 2026-08-25.** It was there on the assumption
that packaging needs a finished app to package. The PWA layer — caching,
updates, persistence, the storage screen — depends on none of the play loop,
and building it created the `@valkyrie/app` package that T-022's release
pipeline had been waiting for. T-018 is unchanged and still open.


Eviction is the risk that matters. A user with a multi-hundred-MB import losing it to storage
pressure has lost an hour of setup and will not distinguish that from the app being broken.
Persistent storage plus an honest storage screen is the mitigation.

Worth deciding here whether the Android PWA is considered a replacement for the current APK or
a complement to it. That decision affects T-022 and how the existing Android users are migrated
— note that the current APK signing situation (keystore committed with a plaintext password)
is a separate problem that a PWA transition would happen to sidestep.

## Progress

**2026-08-25 — the PWA layer is done; installability and the browser-matrix
check are not, and both are explained below.**

New package `@valkyrie/app`, which also gives T-022's release pipeline
something to publish. 27 tests.

**The caching strategy is built around what it must not destroy.** The cache
holds the *app*, never the content: imports and saves live in OPFS, which the
service worker does not touch. A version bump therefore costs a few hundred
kilobytes of re-download rather than the user's several-hundred-megabyte
import. Activation removes only this app's own older caches — anything else in
the origin is left alone, and there is a test for that.

**An update never swaps under the user.** `skipWaiting` is deliberately *not*
called on install; the new worker waits, the shell is told, and it takes over
only when the user accepts. A quest in progress cannot be replaced mid-event.

**Persistence is asked for properly.** A bare `persist()` at load time is
usually refused, so the request is made at the moment the user is about to
spend hundreds of megabytes. The result distinguishes granted, already-granted,
refused and unsupported, because those call for four different things to say —
and the refusal message deliberately does not read like an error, since the
import still works and most browsers grant it later.

**A double-counting bug found while testing the storage screen.** Content packs
live *inside* the download directory, so reporting both counted those bytes
twice and would have told the user they were using more space than they were.
Fixed with an exclusion, and pinned by a test.

Saves are marked unremovable: re-importing is slow but possible, whereas losing
saves loses progress outright, so `reclaim` refuses them.

**2026-08-25 (later) — the app is now runnable.** `npm run dev` serves the
shell; `npm run build:site` produces a deployable build of **73 kB, 23.4 kB
gzipped**, which is the whole port: core, platform, ui and app. Worth holding
against the ADR's rejected alternative — a Unity WebGL build ships roughly
40 MB of engine runtime before any content.

The shell wires together what is finished: the unit system responding to the
viewport, the component set, trait filtering over a quest list, the board
renderer with pan/zoom and hit testing, the event dialog, investigator
selection, and the storage screen. The play loop it will eventually drive is
not finished, so it is a shell rather than the app.

This also makes T-022's deploy step live: it was inert because there was no
`packages/app` to publish.

**One environment quirk worked around:** this machine has two Node installs of
different architectures, and `npx` resolved the x64 one while the dependencies
were built for arm64, so rollup failed looking for a native binary it could not
have. `packages/app/run.mjs` spawns Vite with `process.execPath` instead of
letting PATH decide.

**Not done — installability.** The manifest is written, but the icons it
references do not exist, so the app is not yet installable. Generating them
needs artwork rather than code; the current `PlayerIcon.icns` is a Unity
resource and its licensing for web use has not been checked, which is the same
open question as the fonts in T-016.

**Not done — the browser-matrix verification.** That criterion depends on the
matrix being agreed in T-003, which is still one of the open decisions. Nothing
here has been run in a real browser: the service worker is tested through an
injected scope, which exercises the logic but not the platform.

**Left for you, as the notes ask:** whether the Android PWA replaces the
current APK or complements it. Worth noting it would sidestep the committed
keystore with the plaintext password, which is a separate problem either way.
