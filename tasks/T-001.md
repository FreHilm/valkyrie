## Goal

Determine how imported FFG textures can be displayed in a browser. `ContentData.cs:520`
probes for `.dds`, `.pvr`, `.png`, `.jpg`, `.jpeg`, `.tex`. Neither DDS nor PVR can be
decoded by `<img>`. DXT can be uploaded directly to WebGL via
`WEBGL_compressed_texture_s3tc` on desktop GPUs, but PVRTC has effectively no web support.

## Acceptance Criteria

- [x] Inventory which formats actually appear in a real D2E and MoM import, with counts and total bytes
- [x] Working DXT1/DXT3/DXT5 decode to RGBA in TypeScript, validated against `ContentData.cs:600-660`
- [ ] Working PVRTC path, or a documented decision to transcode PVR at import time instead
- [ ] Benchmark: decode-on-load vs transcode-once-at-import, measured on a mid-range laptop and an Android phone
- [x] Recommendation written up, feeding T-003 and T-014

## Notes

Transcoding once at import is the likely winner: it moves the cost off the hot path and
sidesteps PVRTC entirely. KTX2/Basis is worth evaluating as the stored format.

The Android FFG app ships PVR; the desktop app ships DDS. If the import pipeline normalises
both to one web format, the rest of the app never has to care.

## Progress

**2026-08-25 — done, against a real Mansions of Madness 2.1.6 install.**

**Inventory** (733 textures): DXT5 355, DXT1 300, RGBA32 66, Alpha8 8, RGB24 4.
**There is no PVR** — this task, T-003 and the ADR all assumed DDS *and* PVR,
but PVR is the mobile build's format and a desktop install has none. The PVRTC
criterion is therefore left unchecked: there is nothing here to build it
against, and it would only matter for an Android import.

**DXT decode** is in `packages/platform/src/dds.ts`, verified against **Pillow**
— an independent implementation — over the real corpus: **468 textures
pixel-exact**, covering DXT1, DXT5, RGBA32, RGB24 and Alpha8. A second harness
cross-checks the direct Unity-payload path against the DDS path: 459 textures
agree across two entirely separate routes.

Mutation-tested. Three of four deliberate bugs were caught immediately (a
dropped 5-bit expansion broke 398 of 468 textures). The fourth — the BC1
`c0 > c1` mode comparison — was **not**, because no texture in the corpus pairs
equal endpoints with the punch-through index. That gap is now closed by a
synthetic unit test that does fail under the mutation.

**Storage format — the recommendation changed on measurement.** The ADR said
"PNG first". PNG is not competitive, and the right answer depends on the source:

| source | count | as DDS | WebP lossless | WebP q90 |
| --- | ---: | ---: | ---: | ---: |
| DXT1 / DXT5 | 398 | 68.4 MB | 51.5 MB | **15.5 MB** |
| RGBA32 / RGB24 / Alpha8 | 70 | 64.3 MB | **6.3 MB** | 3.2 MB |

DXT is already lossy, so encoding its output losslessly spends 3.3x the bytes
preserving block artefacts — on the largest map tiles lossless WebP comes out
*larger than the source*. Uncompressed sources are UI art and SDF font atlases,
where lossless already costs under a tenth of source and going lossy would
damage the atlases. So: **lossy q90 for block sources, lossless for the rest.**
PNG for everything would be 83.8 MB against a combined 21.8 MB.

**Not done: the decode-on-load vs transcode-at-import benchmark**, and no
Android measurement. Transcode-at-import is what is implemented, and the
measured import cost (43s for a full MoM library) makes it clearly the right
side of that trade — but the alternative was not built, so this is a reasoned
choice rather than a measured comparison. Recorded rather than claimed.

Details in `webapp/docs/ffg-import.md`.
