## Goal

Drive a scenario from the quest list to its end screen automatically, so the
milestone T-018 claimed — a published community scenario playable start to
finish — is checked by something rather than asserted.

## Acceptance Criteria

- [x] A headless run plays one published scenario from selection to the end-of-quest screen
- [x] It fails on a console error, an uncaught exception, or a state it cannot advance out of
- [x] It distinguishes "the quest is waiting for the player" from "the quest is stuck"
- [x] Runs in CI within a sensible time budget — the fixture playthrough does; the browser harness cannot, see below
- [x] A second scenario added once the first is green

## Notes

Depends on T-024: no scenario can currently reach its end, so this cannot pass
until puzzles are wired.

There is a working starting point in this session's scratchpad — a CDP harness
that presses whatever is actionable, sweeps the canvas for board pieces, wounds
and defeats monsters, and reports where it stops. On Exotic Material it got
through the intro, party setup, two tiles explored, two Cultists killed and a
door unlocked before losing the thread. Its main weakness is that it cannot
tell a board piece from the UI chrome drawn over the same canvas — which T-031
would fix for it, by giving the board real focusable nodes.

## Progress

- 2026-08-28: Raised while auditing the play loop against the C#.

- 2026-08-28: Two halves, because the acceptance criteria as written could not
  both be met by one thing.

  **`packages/app/test/playthrough.test.ts`** plays a fixture scenario from its
  opening event to its end screen — through a puzzle, a monster and the board —
  driven only by what is on screen, in the same DOM a player uses. It runs in
  CI in milliseconds. It is a fixture rather than a published scenario because
  a published one needs art and audio from a licensed install, which never
  enters this repository; that costs coverage of the content pipeline and buys
  a playthrough that runs everywhere.

  It bites. Reverting any of this session's three fixes in turn — puzzles
  unwired (T-024), board pieces unbuilt (T-031), the quest end never handed
  over (T-025) — fails it. Each of those shipped before; this would have caught
  all three.

  **`tools/playthrough/playthrough.mjs`** is the browser harness for the real
  thing, against a real install: `npm run playthrough -- --quest <id>`. It
  presses what a player would press, fails on a console error, an uncaught
  exception, or three idle steps in a row, and says how it got there.

  It played **MoM__ExoticMaterial to its end screen in 158 steps** with no
  console errors — the milestone T-018 claimed and could not show.

  Three things it taught me about itself along the way, all of them the tool
  being naive rather than the port being wrong:

  - The quota spinner carries a `+` just as a monster's health tracker does.
    Pressing the wrong one dials a counter up and down forever, which reads as
    a stuck quest.
  - Submitting the nought a quota opens on means "no successes", so a search
    never finds anything and its token stays to be searched again. It dials
    before answering now.
  - Several scenarios run their opening — sometimes their whole first act — as
    `[UI...]` components rather than events. A presser that only knows about
    dialogs and the board waits for a board that never comes; In Places Unseen
    sat through thirty-two empty rounds before this was fixed.

  One thing that looked like a port bug and was not: at 150ms between presses
  the harness ended up on the main menu mid-quest. At a sane pace it does not —
  it was pressing faster than the app settles.
