## Goal

Replace `ZipManager.cs` (214 lines, DotNetZip) with a browser zip implementation, preserving
the path-traversal protections and fixing the gaps the current implementation has.

## Acceptance Criteria

- [x] All four extract modes ported: `EXTRACT_FULL`, `EXTRACT_INI_TXT`, `EXTRACT_INI_TXT_PIC`, `EXTRACT_SAVE_INI_PIC`
- [x] Path traversal blocked on **every** mode, not just `EXTRACT_FULL` — see the note below
- [x] `ZipSlipTests.cs` ported and passing, extended to cover the selective-extraction modes
- [x] Streaming extraction that does not require holding the whole archive in memory
- [x] Runs off the main thread so large imports do not freeze the UI
- [x] Resources released on the error path (the current C# leaks on exception — see below)

## Notes

Two defects in the current implementation to carry forward as fixes rather than reproduce:

1. The traversal guard at `ZipManager.cs:137-149` only covers `ZIPMANAGER_EXTRACT_FULL`. The
   `ExtractSelectedEntries` calls at lines 160-178 extract by name pattern with no destination
   validation, so an entry named `../../quest.ini` is worth testing against. This matters because
   these paths run on downloaded community content.
2. `ZipFile.Read` at line 133 is not in a `using` block; `zip.Dispose()` sits at the end of the
   try, so any mid-extraction throw leaks the handle.

The traversal check itself (including the trailing-separator handling) is correct and worth
mirroring in the port.

## Progress

**2026-08-25 — done.**

Ported to `packages/platform/src/archive.ts`. All six acceptance criteria met;
36 tests in `packages/platform/test/archive.test.ts`.

**The four modes and their selectors** were reproduced exactly, including the
leading wildcards (`name = quest.ini` matches at the root, `*quest.ini` reaches
into a subdirectory — the C# comment notes the latter is required on Android),
and the two-pass `INI_TXT_PIC` shape where `quest.ini` must be written before
the image it names can be read.

**On the traversal guard.** Rather than infer what the selective modes do, the
selective extraction was run against real DotNetZip with an archive containing
`../../escaped-quest.ini`. The selector `name = *quest.ini` *does* match the
traversing entry and hands it to extraction — confirmed by execution. On
DotNetZip 1.16.0 the library itself then sanitises the path, so it lands inside
the target. Two conclusions, which should not be conflated:

- `ZipManager` contributes no protection of its own in these modes;
- the protection that exists comes from the bundled library.

`unity/Assets/Plugins/Ionic.Zip.Unity.dll` reports **1.9.1.6**, far older than
the 1.16.0 tested, and NuGet flags 1.16.0 itself with
[GHSA-xhg6-9j5j-w4vf](https://github.com/advisories/GHSA-xhg6-9j5j-w4vf) — so
the bundled build is inside the affected range. **This was not demonstrated
against the shipped DLL**; that needs a harness around the Unity assembly,
which was not built. Adding a destination check to `ZipManager`'s selective
modes is a small change and would remove the dependency on library behaviour
entirely. Worth doing in the Unity app regardless of this port.

**Streaming and threading.** `extractStream` consumes an async iterable of
chunks, so peak memory is one entry rather than the archive; unselected entries
are never decompressed. fflate's async `unzip` spawns a real worker (Blob-URL
`Worker` in the browser, `worker_threads` in Node), so inflate is already off
the main thread, and the module touches no DOM API so a caller can run the
whole extraction in its own worker. Tests assert streaming and buffered
extraction put identical files on disk.

**A bug found while testing streaming:** fflate's streaming reader skips bytes
it does not recognise, so a truncated or corrupt download extracted nothing and
reported *success* — the user would get a silently empty quest.
`extractStream` now validates the leading PKZIP signature and throws, while
still accepting a legitimately empty archive.

**Also closed here: `FindLocalisedMultimediaFile`.** The conformance ledger had
its 13 cases listed as `deferred` against T-011, which was already marked done
— so the ledger was pointing at a closed task. Ported to
`packages/platform/src/multimedia.ts`, all 13 cases migrated by name.

Verified differentially. `Quest.cs` cannot be compiled outside Unity, so
`tools/differential/multimedia/extract.mjs` slices the one Unity-free overload
out of the real source by brace-matching rather than copying it, and fails
loudly if the signature moves. **0 divergences across 5 seeds x 4,024 cases.**

The first run diverged twice, and both were the port's *filesystem* being more
forgiving than a real one, not the resolver:

- a name of `./Tile.png` missed its localised file, because lookups did not
  resolve `.` segments — and quest inis written by scenario authors do contain
  `./` prefixes;
- a name of `Tile.png/` matched a file, where POSIX and .NET both require a
  trailing separator to mean a directory.

Both changed which path the resolver returned. Fixed in the filesystem layer
across all three implementations and asserted by the shared `describe.each`
suite. `OpfsFileSystem` was wrong in both ways with no test that would have
caught it — it would have failed only in a browser.

Deviations recorded in `webapp/docs/archive-port-deviations.md` and
`webapp/docs/multimedia-port-deviations.md`. Ledger updated: `ZipSlipTests` and
`FindLocalisedMultimediaFileTests` both `ported`; the ledger now also scans
`packages/platform/test`, which it previously missed. Full suite: 782 tests,
lint/format/typecheck clean, all six differential harnesses at 0 divergences.
