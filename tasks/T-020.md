## Goal

Replace `Audio.cs` and the Unity `AudioSource` usage with Web Audio, and settle how imported FFG
audio is decoded.

## Acceptance Criteria

- [x] Music and sound effect playback with independent volume control, matching current options
- [x] Quest-supplied `.ogg` files play (the editor already scans for `*.ogg`)
- [x] Imported FFG audio plays — verify what `FSBExport.cs` and `OggVorbisHeader.cs` actually produce
- [x] Autoplay policy handled: audio starts only after a user gesture, without appearing broken
- [x] Audio does not block or stutter the main thread during board interaction
- [x] Sensible behaviour when a file is missing or fails to decode

## Notes

**Dependency on T-014 removed on 2026-08-25.** It was there because "imported
FFG audio plays" needs the FFG asset pipeline. That criterion is still **not
met** and is left unchecked. Everything else — playback, volumes, the autoplay
gate, quest `.ogg` files, error handling, and the Ogg muxer — needs nothing
from T-014 and is delivered. Blocking the whole task on a dependency that is
itself blocked on licensed files nobody has would have left finished, verified
work sitting open indefinitely. T-014 is unchanged and still todo.


Worth checking early whether the 26.7k LOC vendored Ogg Vorbis encoder is needed at all. If
`FSBExport` extracts raw Vorbis and `OggVorbisHeader` only reconstructs container headers, then
`decodeAudioData` may accept the result directly and that entire dependency disappears from the
port. This overlaps with T-002 and should be answered there if possible.

Browsers decode Ogg Vorbis natively except on Safari, which needs checking against the target
browser matrix set in T-003.

## Progress

**2026-08-25 — done except the one criterion that needs the licensed FFG files.**

Ported to `packages/platform/src/audio.ts` (Web Audio) and
`packages/platform/src/ogg.ts` (the Ogg muxer). 43 new tests.

**The notes' question is answered, and demonstrated rather than argued: the
26,669-line vendored Ogg Vorbis encoder is not needed.**

`FSBExport` never encodes any audio. FSB5 stores Vorbis packets with their three
headers stripped, and the audio packets are copied through verbatim. The encoder
is used for three things only: the identification header, the comment header,
and Ogg page framing. The setup header is not built at all — `OggVorbisHeader.cs`
is three fixed blobs looked up by CRC, 590 lines of data rather than code.

`ogg.ts` replaces all three in **~200 lines**, and
`tools/differential/ogg` compiles the vendored encoder **unmodified** to prove
it: **0 divergences, byte for byte, across 5 seeds x 836 cases**.

**I did not trust that first-run pass, and it turned out I was right not to.**
Mutation-testing the harness — introducing a wrong CRC polynomial, a missing
beginning-of-stream flag, a wrong granule position, a wrong lacing count —
initially caught **none** of them. The harness was importing
`@valkyrie/platform`, which resolves to the built `dist/`, so it was comparing
against a stale build and would have looked healthy indefinitely. The `ogg`,
`multimedia` and `remote` harnesses now import source paths directly. After the
fix all four mutations are caught, each at exactly the right byte offset (5 =
header flags, 6 = granule, 22 = CRC, 6459 = segment table).

**A bug found in my own first implementation:** a playlist where no track could
be decoded wrapped forever — infinite recursion, taking the tab with it. The C#
does not have this because a failed `UnityWebRequest` never adds the clip,
leaving the list shorter. Now it stops after one pass over the list.

**A second instance of the locale bug** from T-005: `Audio.Start` reads the two
volumes with `float.TryParse` under the machine culture, so on a comma-decimal
locale a stored `0.8` fails and `TryParse` leaves **0** — the app comes up
silent with the slider showing 80%.

**Deviations** (`webapp/docs/audio-port-deviations.md`): invariant volume
parsing at float32 precision; music requested before the autoplay gesture is
held rather than dropped; the fade is a scheduled ramp instead of a per-tick
subtraction tied to the physics rate; a generation counter stops a superseded
playlist advancing the current one; comment lengths measured in UTF-8 bytes
rather than UTF-16 code units, which the C# gets wrong for any non-ASCII tag.

**Not done — blocked on T-002/T-014.** "Imported FFG audio plays" needs the
licensed app files to run `FSBExport` end to end. The muxing half is done and
verified byte-identical; the FSB parsing half needs `AssetStudio` and real
archives. What is settled is that the port and the original produce the same
bytes, so whatever one yields the other will too.

**Still open for you:** the notes ask about Safari, whose Ogg Vorbis support
depends on the OS version. That is a browser-matrix decision and belongs in
T-003. If Safari must be supported without native Vorbis, a WASM decoder is the
fallback.

Full suite: 981 tests, lint/format/typecheck clean, all eight differential
harnesses at 0 divergences.

**2026-08-25 (later) — the blocked criterion is now met.** A licensed Mansions
of Madness install became available, and the FSB5 half was built in T-014:
`packages/platform/src/fsb.ts` parses the container and hands the packets to
the muxer verified here.

**173 of 174 real streams come out byte-identical to `FSBExport`**, and all 173
decode cleanly under a full ffmpeg decode — so imported FFG audio does play.

The one exception found a defect in the shipped app rather than in the port:
for a stream whose setup-header CRC is not one of the three known ones,
`GetHeader` returns null and **`FSBExport` writes the file anyway**. ffmpeg
rejects the result ("Header processing failed"). It fails silently; the user
only finds out when the sound does not play. The port refuses and reports it.

This also settles the question this task raised: the vendored encoder was not
needed, and the ~200-line replacement handles real content end to end.
