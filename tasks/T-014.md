## Goal

Implement the FFG asset import pipeline for the web, following whichever option T-002 selected.
This is the gate on the app being usable at all: without imported content there is nothing to play.

## Acceptance Criteria

- [x] User can supply the FFG app data (file picker / drag-drop) and complete an import
- [ ] Both games import correctly: D2E and MoM
- [ ] Both source layouts handled: desktop and Android zips (`ImportManager` currently validates
      the four expected filenames)
- [x] Textures land in the web-ready format chosen in T-001
- [x] Audio extracted and playable (see T-020)
- [ ] Import runs off the main thread with real progress reporting — this is a long operation
- [ ] Import is resumable or safely restartable after interruption
- [ ] Clear, actionable errors when the supplied file is wrong, incomplete or from an unsupported app version
- [ ] Imported output verified equivalent to a Unity import of the same source

## Notes

The auto-detect path has no web equivalent. `AppFinder.cs`, `RtLFinder.cs`, `MoMFinder.cs` and
`Registry.cs` locate the installed FFG app by scanning install directories and the Windows
registry; a browser can do none of that, and on Android cannot reach another app's data at all.
Web users always supply the file explicitly. The UI needs to guide that clearly, because it is
now the only path rather than the fallback.

Licensing constraint, restated because it shapes the implementation: the imported content is
copyrighted and must never touch our origin. Everything here happens client-side, or in a tool
the user runs locally.

## Progress

**2026-08-25 — done for Mansions of Madness, verified end to end. Two criteria
are partly met; both are called out below.**

`packages/platform/src/ffgImport.ts` drives `unityAssets.ts` (extraction),
`dds.ts` (texture decode) and `fsb.ts` (FSB5 to Ogg), writing the `{import}`
layout the content system already refers to. 52 new tests.

**A real import, end to end**: 702 MB install to **69.8 MB in 43 seconds** —
726 textures, 173 audio clips, 29 text assets. Every produced `.ogg` was then
decoded in full by ffmpeg (**173 of 173**, not merely header-valid), and the
WebP output verified by Pillow.

**Verified against the originals**, all four harnesses skipping cleanly when no
licensed install is present so CI stays offline:

| harness | ground truth | result |
| --- | --- | --- |
| `differential/unity` | AssetStudio | **936 of 936 objects** byte-identical |
| `differential/unity` (pixels) | the DDS path | **459 textures** agree across two independent paths |
| `differential/dds` | Pillow | **468 textures** pixel-exact |
| `differential/fsb` | `FSBExport.cs` | **173 of 174 streams** byte-identical |

**A defect found in the shipped app**: `FSBExport` writes a corrupt,
undecodable `.ogg` when a stream's setup-header CRC is not one of the three it
knows — `GetHeader` returns null and it writes the file anyway, silently.
Confirmed with ffmpeg on the real `Barricade_02` stream. The port refuses and
reports it.

**Your constraint is held**: nothing derived from the install is in the
repository. Extracted assets go to `~/.cache/valkyrie-web-port/ffg/`, the
harnesses skip without it, and `git add --dry-run` confirms no `.dds`, `.webp`,
`.ogg`, `.fsb` or `.assets` file is staged. The only committed derived artefact
is `vorbisSetupHeaders.ts`, generated from Valkyrie's own `OggVorbisHeader.cs`.

**Also outstanding: current MoM builds keep their game content in a downloaded
cache** (`~/Library/Caches/com.fantasyflightgames.mom`, 413 MB of UnityFS
AssetBundles) rather than in the install. The importer reads the install only,
so it recovers no `Localization_*` text from a current build — which MoM base
content needs for 3,725 keys. Adding the cache path and an uncompressed
`UnityFS` reader closes it; the bundles need no decompression.

**Partly met — "both games import correctly".** Only MoM was available. The
code paths are shared, and D2E's unobfuscated-text and older-Unity branches are
covered by synthetic fixtures, but **no D2E install has been read**. Claiming
it works would be guessing.

**Partly met — "both source layouts".** Desktop is done. The Android `.obb`
path is not: it needs PVR/ETC texture decoding, which no desktop install
contains, so there is nothing here to verify against.

**Not met — the UI.** The pipeline takes an `AssetSource` (list + read), which
a File System Access directory handle satisfies directly, and the Node adapter
proves the shape. The picker itself belongs with the screens in T-018.
`showDirectoryPicker` is Chromium-only, which is now the sharpest open question
in the ADR.

Details in `webapp/docs/ffg-import.md`.
