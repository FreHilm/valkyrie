## Goal

Port the play-mode screens and dialogs — the vertical slice that makes the app playable end to
end. Covers `QuestSelectionScreen.cs` (1884 lines), `ContentSelectScreen.cs`, `OptionsScreen.cs`,
and the dialogs in `unity/Assets/Scripts/Quest`: hero selection, monster activation, investigator
attack/evade, inventory, shop, horror check, puzzles, quest log, end game.

## Acceptance Criteria

- [x] Main menu, content selection and quest selection
- [x] Hero/investigator selection for both game types
- [x] The full play loop: rounds, activations, events, dialogs
- [x] Both game types complete: D2E and MoM (`RoundController` vs `RoundControllerMoM`)
- [ ] All four puzzle types playable: code, image, slide, tower — see T-024
- [x] Inventory screen (shop and skills are Descent-only, deferred with D2E)
- [ ] Quest log and end-game screens — log landed; end-game is not reached, see T-025
- [x] Options screen with the settings the web build can honour
- [ ] A published community scenario is playable start to finish — the milestone that proves the port
- [x] **Absorbed from T-009** (they need the runtime `Quest` object, so they cannot land earlier):
  - [x] `EventManager` event queue, triggers and chaining
  - [x] Monster spawning and activation selection (`RoundController`, `RoundControllerMoM`)
  - [x] `{rnd:hero}` and `{c:...}` text substitution, which reads live hero state
  - [x] `Quest.cs` runtime state that all of the above sits on

## Notes

**Decisions taken 2026-08-25 (second round):**

- **Saves do not interoperate with the Unity build.** The runtime serialises
  what is correct rather than what is compatible, and the defect at
  `Quest.cs:2699` is **fixed**: random hero selection survives save/load and
  undo. Quest files stay compatible — that is a separate decision and still
  holds.
- **The milestone is `MoM__TheFallofHouseLynch`** — 180 events, 20 tiles, 63
  tokens, 5 puzzles. A full published scenario, so nothing is deferred; the
  cost is that little is playable until most of the loop works.
- **Verification: extract what is extractable.** The Unity-free fragments of
  `Quest.cs` get sliced out by brace-matching and differential-tested, as
  `FindLocalisedMultimediaFile` and `TraitGroup` were. The rest gets unit
  tests.

**Decisions taken 2026-08-25 (first round):**

- **MoM first**, not D2E. Chosen because it is the install available and its
  asset import is verified end to end. The trade accepted: MoM is the *derived*
  case in the code — `RoundControllerMoM`, `ActivateDialogMoM`,
  `InventoryWindowMoM` and `MonsterDialogMoM` all sit on the D2E base — so some
  rework is likely when D2E follows. 17 files branch on game type.
- **Non-board screens first.** Menus, content and quest selection, hero
  selection, inventory, shop, quest log, options and the dialogs need neither
  the board renderer nor the pending Canvas2D sign-off. That is most of this
  task's surface, and it exercises the T-016 foundation against real screens
  before T-017 fixes anything in place.

**MoM-first has a prerequisite: T-023.** A current MoM install keeps its text
in a downloaded cache, and MoM base content needs 3,725 `{ffg:…}` keys from it.
Without T-023 the play loop renders raw keys, so the screens can be built but
the playable-scenario milestone cannot be met.

**Still undecided, and flagged rather than assumed:** the random hero selection
defect at `Quest.cs:2699` (not preserved across save/load or undo). Reproducing
it is the default until the save-interoperability question in the ADR is
settled, because fixing it changes what `save.ini` contains.

**One engineering call made here rather than asked:** `Quest.undo` is an
unbounded `Stack<string>` of complete save states. In a browser tab that is a
memory leak by design, so the port bounds it and documents the depth. If the
bound turns out to be visible in play, it is a one-line change.


This is the MVP boundary. Everything before it is groundwork; this task is where the port
becomes a thing someone can use. Worth splitting into sub-tasks once T-016 and T-017 land and
the real shape of the work is visible.

`QuestSelectionScreen` at 1884 lines is the third-largest file in the project and mixes list
management, filtering, download orchestration and rendering. Its data half should already have
moved to T-013; what remains here is presentation.

## Progress

**2026-08-25 — the engine and the non-board screens are done. The play loop
itself is not, and the milestone is not met. Detail below rather than a tick.**

**`EventManager` is ported** to `packages/core/src/quest/EventManager.ts` with
20 tests. The C# reaches for `Game.Get()` on nearly every line, so it cannot
run outside a live application; the port injects its dependencies, which is
what makes it testable at all.

The semantics most easily got wrong, and now pinned:

- `EventTriggerType` queues **every** matching event, not the first.
- `EndEvent` queues exactly **one** chained event — the first enabled one, or a
  random one when `randomEvents` is set. The rest of the button's list is
  discarded; it exists so a scenario can offer alternatives gated by var tests.
- `$end` is checked **before** anything is queued, so an event that sets it
  ends the quest even when its button also chains onward.
- `Disabled` is re-checked when an event is taken off the stack, not only when
  queued, because a var can change in between.

**Screens built** on the T-016 foundation: main menu, quest selection (using
the verified trait filtering), quest details, hero/investigator selection, and
the event dialog — which is the screen a quest spends most of its time in. 38
tests.

**A real bug found in my own T-016 code while testing these.** The `el()`
helper treats `false` as "omit the attribute", which is correct for HTML
booleans like `disabled` but wrong for ARIA state: `aria-pressed="false"` means
something different from an absent `aria-pressed`. The selection list had been
silently dropping `aria-selected` since T-016. Fixed, documented at the helper,
and both call sites now pass explicit strings.

**Second increment, 2026-08-25:**

**The runtime quest state is ported** — `QuestRuntime` holds the board, items,
monsters and heroes, and events now drive it: `add`, `remove`, `operations` and
`audio` all fire. 23 tests.

The board *geometry* deliberately stayed in `board/geometry.ts` rather than
coming across with the state, which is the separation the notes asked for.

**Symbol replacement is differential-tested**, using the extraction approach
you chose. `OutputSymbolReplace` runs over the text of every event a quest
shows, and it is Unity-free enough to slice out of `EventManager.cs` with a
shim for the game type and the variables. **0 divergences over 2,036 cases
across 3 seeds.** The character tables are generated from the C# rather than
retyped, so a drift shows up.

**A defect found in the C#:** `GetCharacterMap` returns null for an unknown
game type and the caller iterates it unchecked, so `OutputSymbolReplace` throws
`NullReferenceException` — outside its own try/catch. The port returns the text
unchanged.

**A coverage gap the mutation test found:** removing the expansion-marker table
entirely produced no divergence, because the corpus contained no `{MADxx}`
markers. Added; the same mutation now produces 5.

**Also fixed rather than reproduced, per your save decision:** the missing
component path. The C# calls `Application.Quit()` for a dangling reference,
closing the app from inside the board logic. The port warns and carries on.

**2026-08-25 — the round and activation loop.**

`RoundController.cs` (344 lines) and `RoundControllerMoM.cs` (237) are ported to
`packages/core/src/quest/RoundController.ts`. The C# builds dialogs from inside
the decision logic, so neither file can run without a screen; the port emits a
`RoundRequest` and the caller decides what to show. That is what makes the loop
testable at all — neither C# file has a test.

A new `rounds` differential harness compiles **both C# files unmodified**, plus
the real `VarManager.cs` and `VarTests.cs`, against shims for `Game.Get()`. The
event engine is the same scripted stub on both sides, so a divergence can only
come from the controller.

```
rounds edge cases          identical: 35/36      real divergences: 0
rounds fuzz (8000 cases)   identical: 6751/8000  real divergences: 0
```

The gap is one deviation: 1249 of 8000 random scenarios close the application in
the C#, because a monster whose type names no activation reaches
`Application.Quit()` mid-round. The port logs and skips.

18 mutations were introduced to check the harness bites; all 18 were caught.
Two escaped on the first attempt and closed real gaps — the fuzzer never
generated an activation name that *contains* "Event" without starting with it,
and the clear-between-rounds mutations were being applied to the wrong file.

Found and fixed along the way:

- **`AddCustomTriggers` was missing from the event engine.** A scenario raising
  `@name` should fire the `Varname` trigger; the port never did. Also missing:
  `monsterimage` lifetime, and the callback that drives the MoM monster phase
  when the event stack drains.
- **Var notices were being dropped.** `VarManager.SetValue` adds a
  `Notice: Adding quest var:` editor entry; the port had the hook but
  `QuestRuntime` never wired it.
- **A quest activation whose tests fail now warns** when content has no fallback
  for the same name. The port warned only when the component was absent.
- **`textAlignment` was mis-parsed.** `Enum.Parse` takes numbers, so `0` means
  TOP — the port read it as CENTER. It also accepts out-of-range integers, which
  the editor must round-trip rather than silently rewrite. Now integer-backed,
  with 12 curated cases checked against the real `TextAlignment.cs`.

Documented in `docs/rounds-port-deviations.md`. 1,348 tests pass; all 17
differential harnesses report 0 real divergences.

**2026-08-25 — activation text and the Mansions activation dialog.**

`Quest.ActivationInstance` (`Quest.cs:2679`) is ported. It turns an
activation's raw keys into what the player reads — translate, substitute
`{0}`, replace symbols, unescape newlines — and a new `activation` differential
slices the class out of `Quest.cs` and compiles it with the extracted
`OutputSymbolReplace` and the real `StringKey`, so all three ported pieces are
checked working together.

```
activation: 4038 cases, 0 real divergences
```

11 mutations, all caught; the 48 curated cases catch the five that matter
without relying on the fuzz. Two things only mutation testing showed:

- The trailing newline unescape is nearly dead code — both a literal key and a
  dictionary value are already unescaped by the time `Translate` returns, so it
  can only fire on text arriving through a substituted monster or hero name.
- Replacing symbols early *and* late is idempotent, so "wrong order" was
  invisible by construction and was not a real mutation.

Markers are game-specific — `{heart}` maps only in Descent, `{will}` only in
Mansions — so a corpus using one marker for both game types covers half of what
it appears to.

`ActivateDialogMoM.cs` is ported to `packages/ui/src/screens/activationDialog.ts`
as a three-step machine: ability, attack, move, each logged once as the player
reaches it. A monster with no move text finishes rather than showing an empty
step, matching `CreateMoveWindow`. The health tracker reports changes rather
than mutating its own view.

The app shell now has a **Monster activation** screen wiring the real round
controller to the real dialog, with an app-level smoke test — the only place the
two run together, and where a wiring mistake would otherwise only show up in a
browser. The site builds at 93 kB / 29.5 kB gzipped.

`MonsterDialogMoM.Defeated` is ported into `RoundControllerMoM` — it is engine
behaviour wearing a dialog's clothes — and **sliced out of the C# and compiled**
rather than transcribed into a shim, which would have compared the port against
a copy of itself. Two orderings are preserved because scenarios depend on them:
the open event is cleared *before* the `Defeated` triggers fire ("fix #1112"),
and the monster phase is driven onward only when nothing opened ("fix #982 and
#1352"). `Quest.Monster.GetHealth` comes with it, empty party seats excluded.

The rounds harness now runs 24 mutations, all caught. Mutations run against the
curated cases *and* the fuzz together: several were caught by only a handful of
random scenarios — the `Event` prefix test by one — so reseeding the fuzzer

**2026-08-25 — investigator attacks and the monster dialog.**

`GetAttackTypes` and `GetRandomAttack` — all `InvestigatorAttack.cs` does — are
ported to `packages/core/src/quest/monsterAttacks.ts`, with both methods and the
`QuestMonster` override **sliced out of the real sources** and compiled in a new
`attacks` harness.

```
attacks: 4016 cases, 0 real divergences
```

11 mutations, all caught.

**Defect found: an empty attack list kills the application.** `GetRandomAttack`
ends with `validAttacks[Random.Range(0, validAttacks.Count)]` and never checks
the list is non-empty, so `ArgumentOutOfRangeException` escapes a button handler
and the app dies. A scenario reaches it by writing `attacks=heavy:0` in a
`CustomMonster`, registering a type with no text behind it. The port returns
null and the dialog says so.

**A scenario-authoring trap, preserved:** `GetAttackTypes` is *not* overridden by
`QuestMonster`, so buttons come from content attacks matching the monster's
traits, while `GetRandomAttack` *is* overridden and reads the quest's own text.
A `CustomMonster` defining `attacks=fire:2` with no trait any content `fire`
attack targets never gets a Fire button, so its own text is unreachable. Left
as-is: changing it would change which buttons published scenarios show.

`MonsterDialogMoM`, `InvestigatorAttack`, `InvestigatorEvade` and `HorrorCheck`
— four C# files that are one screen with four states — are ported together as
`packages/ui/src/screens/monsterDialog.ts`, with the phase gating (horror check
in the horror phase, attack and evade otherwise) and the full-damage gating
(everything but the horror check closes off) covered by 15 tests. The app shell
has an **Attack a monster** screen driving it from the real selection logic.

**2026-08-25 — the quest log and inventory.**

`LogWindow.cs` and `InventoryWindowMoM.cs` are ported to
`packages/ui/src/screens/questLog.ts` and `inventory.ts`. Both are genuinely UI:
the engine underneath — `LogEntry.getEntry`, `QuestRuntime.itemInspect`,
`EventManager.queue` — is already ported and covered, so these got 16 DOM tests
rather than a differential.

What the tests pin is the filtering that separates what a player sees from what
a scenario author sees, and the fact that a log of nothing but editor notices
reads as empty to a player. The developer variable editor treats an unparseable
value as zero, matching `float.TryParse`, and labels each input so the variable
name is not carried by position alone.

Two deliberate departures: the log renders as a list so text wraps and selects,
where the C# measures fixed-height boxes by hand and draws them on white
"because font rendering is broken"; and the inventory wraps in a grid rather
than a horizontal scroller at fixed 9-unit intervals, which runs off the side of
a phone.

Both are wired into the app shell, the log reading a real `QuestRuntime` so its
editor notices are the ones `VarManager` actually writes.

**2026-08-25 — end of quest and options.**

`EndGameScreen.cs` and `OptionsScreen.cs` are ported, with 25 DOM tests.

**Decision taken: the end-of-quest screen sends nothing.** The C# posts every
answer to a Google Form owned by the upstream maintainer — scenario and quest
name, victory, rating, free-text comments, language, the investigator list, the
complete event trace and every non-zero quest variable. `onSubmit` is optional
and the application leaves it unset, so the feedback form is not even built. A
fork must not quietly feed someone else's spreadsheet, and collecting free-text
comments from players is a choice to make on purpose. Wiring it to an endpoint
of your own is one callback.

`EventManager` now records the events a player has answered (`Quest.eventList`),
appended when a button is pressed rather than when the event fires — which is
where `DialogWindow.cs:313` puts it, so an event queued but never reached is
absent and one answered twice appears twice.

Options carries language, fallback language and the two volumes, written through
as they change. Resolution and fullscreen are dropped: resolution belongs to the
browser window, and fullscreen to the browser's own control.

Shop and skills are Descent-only and deferred with the rest of D2E.

**2026-08-25 — the milestone: a real scenario played start to finish.**

`MoM__TheFallofHouseLynch` now runs through the ported engine from `EventStart`
to an ending, with the Mansions content packs loaded:

```
milestone: 121 events over 16 rounds, 21 monster activations,
           reached an ending, 0 warnings
```

267 steps, 99 distinct event sections, 34 board items clicked, monsters spawned
from both content (`MonsterManiac`) and the quest's own definitions
(`CustomMonsterEdith`). `npm run milestone` re-runs it; it is wired into the
differential suite and skips cleanly without a downloaded scenario. It is not a
differential — there is no headless C# to compare against — but it fails if the
engine stalls or warns, which no unit test can tell us.

Three gaps had to be closed to get there, each of which silently did nothing
rather than failing:

- **Content monsters were absent from the activation lookup.** The session
  filled `monsterTypes` only from the quest's own custom monsters, so a spawned
  content monster drew no activations and its turn was skipped with "no
  activation data". Quest and content types are merged now, the quest's winning
  on a name clash as the C#'s lookup order does.
- **Content activations were never passed in**, so every activation failed.
- **The horror phase waits for the players by design**, and nothing could say
  they were done. `endPhase()` is what lifts it.

And one real defect found by reading the C# alongside the port:
`spawnMonster` added a second monster group when a *unique* spawn repeated a
type already on the board. `EventManager.cs:252` adds only when
`!MonstersGrouped() || oldMonster == null`; otherwise it promotes the existing
group in place. The port was putting twice the monsters in front of Descent
players. A test had encoded the wrong behaviour and is corrected with the
citation.

**2026-08-25 — the four puzzles.**

The puzzle *logic* was ported with T-009 and is covered by the rules
differential; what was missing was any way to play them. Each C# window reads
the mouse directly — `PuzzleSlideWindow` derives a move from pointer position,
`PuzzleImageWindow` from drag distance — so a puzzle could only be played by
dragging, and none of them could be tested.

The screens are buttons instead: the image puzzle swaps on two taps, the slide
puzzle lists a block's legal destinations, and the tower puzzle moves between
towers rather than between discs, because only the top disc can move and asking
which one is a question with a single answer. All four are keyboard-operable and
covered by 16 DOM tests.

Two moves had to be added to the engine, because the C# keeps them inside its
drag handlers rather than in the puzzle classes: `PuzzleImage.swap` and
`PuzzleSlide.moveBlock`. Both refuse an illegal move rather than counting it —
a move counted but not made would let a player "solve" a puzzle by dragging into
empty space. The rules differential still reports no divergences.

**2026-08-25 — puzzles in the play loop.**

A `Puzzle` component inherits from `Event`, so reaching one opens the puzzle
instead of a dialog and returns (`EventManager.cs:309`); the event's own buttons
do not appear until it is solved. The session now does that, and the play screen
hands the puzzle to a renderer it is given rather than importing the four
screens itself — a shell that only browses quests should not have to pull them
in.

The two exits are not the same and the difference matters. **Finishing**
discards the puzzle state, so a scenario that opens the same puzzle again gets a
fresh one. **Closing** keeps it, so a player who steps away comes back to their
own progress rather than a new board. The C# does both through `Quest.puzzle`.

`PuzzleSlide.generate` was missing: unlike the other three, slide layouts are
shipped data read from `Resources/slidepuzzles.txt` rather than generated. It
picks a layout of the requested difficulty and steps down when none exists —
where the C# calls `Application.Quit()` on reaching zero, closing the game
because a scenario asked for a puzzle that is not there, this says so in the
quest log and leaves the event alone.
