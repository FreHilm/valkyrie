## Goal

Port the rules engine: `VarManager.cs`, `VarTests.cs` (406 lines), `EventManager.cs`
(1006 lines), the puzzle logic (`PuzzleCode.cs`, `PuzzleImage.cs`, `PuzzleSlide.cs`,
`PuzzleTower.cs`), and `QuestMonster.cs`.

These files already sit on the engine-free side of the line — they import `UnityEngine` but use
none of the heavy types — so they port rather than get rewritten.

## Acceptance Criteria

- [x] Variable system ported: assignment, arithmetic, comparison operators, all built-in vars
- [x] `VarTests` boolean expression evaluation matches exactly, including operator precedence
- [ ] Event queue, triggers, conditions and chaining ported from `EventManager`
- [x] Puzzle generation and solution checking ported; verify against `PuzzleGenerator` output
- [x] Cases from `VarManagerTests.cs`, `VarTestsTests.cs`, `EventManagerTests.cs`,
      `PuzzleTests.cs` and `PuzzleCodeTests.cs` pass
- [ ] Monster spawning, placement and activation selection ported
- [ ] Both game types exercised — D2E and MoM diverge here (`RoundController` vs `RoundControllerMoM`)

## Notes

Puzzle generation must be deterministic and match the Unity implementation, or saves become
incompatible across the two builds. Pin down the RNG explicitly rather than relying on whatever
the platform provides — this is a place where a silent divergence would be very hard to
diagnose later.

The MoM/D2E split is currently handled by parallel subclasses driven by `GameType`. Porting is a
reasonable moment to reconsider that shape, but only if T-003 decided so; otherwise mirror it.

## Progress

### 2026-08-25

Ported the pure half and verified it. 45 new tests (440 total), 96.87%
statement coverage, 8,081 differential cases with zero real divergences.

**Done:** `VarManager` (variable store, arithmetic, condition evaluation) and
all four puzzle types (code, image, slide, tower) — generation, save/load and
solution checking. `VarTests` came earlier, with T-008.

**Moved to T-018.** `EventManager.cs` is 1,006 lines and almost all of it
drives the *running* game: `game.CurrentQuest`, hero selection, monster
placement, dialog windows. It cannot be ported or tested without `Quest.cs`
(2,817 lines of runtime state), which no task owns explicitly. What moves:

- the event queue, triggers and chaining
- monster spawning, placement and activation selection
- `{rnd:hero}` and `{c:...}` text substitution, which reads live hero state

T-018's acceptance criteria should absorb these. Flagging rather than silently
narrowing the task.

**Three bugs the corpus found in the port:**

1. **The nested condition must short-circuit.** The C# evaluates a
   parenthesised group as `result && Test(remaining)`; C#'s `&&` skips the
   recursive call when `result` is already false, so the variables that call
   would create are never created. The port had hoisted the recursion into a
   variable, producing extra quest variables and consuming `#rand` draws the
   C# never draws. 17 fuzz cases caught it.
2. **Quest variables are 32-bit floats.** `Dictionary<string, float>`, so
   `7 / 6` must print `1.1666666`, not the double expansion. Every result is
   now `Math.fround`ed and rendered at float precision.
3. **Negative zero prints with its sign** in .NET but not in JS — visible in
   the quest log text.

**Deviations:** `TrimQuest` no longer throws on a single-character variable
name (the C# calls `Substring(0, 2)` unguarded), and a malformed
`VarOperation` no longer throws — both carried over as documented.

**Preserved bug worth knowing:** several serialisers append `item + separator`
then chop one character, so an empty list loses the field's `=` — `guess`
instead of `guess=`, `1` instead of `1=`. Saved games contain these lines, so
`appendTrimmed` models the pattern deliberately.

Full notes in `webapp/docs/rules-port-deviations.md`.
