## Goal

Port `QuestData.cs` (2513 lines) and the quest component model — the second-largest file in the
project and the schema every community scenario is written against.

## Acceptance Criteria

- [x] Every quest component type ported: Event, Tile, Door, Token, Monster, MPlace, Spawn, Puzzle, StartingItem, QItem, CustomMonster, Activation, UI
- [ ] Quest package (`.valkyrie`) loading ported, including partial-load for the quest list
- [x] Cases from `QuestComponentTests.cs` (2880 lines, the largest test file) pass
- [x] A corpus of published community scenarios loads without error, compared against Unity output
- [x] Quest format version gating matches `FormatVersions.cs`

## Notes

Backwards compatibility is the whole job here. Hundreds of published scenarios target the
current schema, and there is no way to migrate content that lives in other people's GitHub
repositories. The ported parser must accept everything the Unity one accepts.

Build the reference corpus early — a script that pulls the published scenario list from
`valkyrie-store` and loads every one is the strongest regression signal available for this task.

`Quest.cs` (2817 lines, runtime state) is deliberately not in scope here; it depends on the
rules engine and is split across T-009 and T-015.

## Progress

### 2026-08-25

Ported and verified. 89 new tests (395 total), 97.28% statement coverage.

**Real content had to be downloaded.** No quest content ships with the repo —
scenarios come from `valkyrie-store` and `valkyrie-questdata` at runtime.
`tools/differential/quest/fetch-real.mjs` pulls a sample; `real-content.mjs`
yields an empty corpus when it is absent, so CI still runs offline.

| Corpus | Cases | Real divergences |
| --- | ---: | ---: |
| Hand-written edge cases | 118 | 0 |
| Fuzz | 8,000 | 0 |
| **228 published quest manifests** (every D2E and MoM scenario in the store) | 228 | 0 |
| **12 downloaded scenarios, 2,744 real sections** | 133 | 0 |

The 12 scenarios cover every component type: 1,695 Events, 408 Tokens, 146
Tiles, 119 Spawns, 112 QItems, 75 UIs, 49 MPlaces, 27 Activations, 23
CustomMonsters, 18 Puzzles, 18 Doors.

**VarTests came early.** `QuestComponent` cannot be ported without it — a real
cycle in the task graph, since T-009 nominally owns it. T-009 keeps
`VarManager` and `EventManager`.

**Three bugs the corpus found in the port:**

1. **`TextAlignment` is TOP/CENTER/BOTTOM, not LEFT/CENTER/RIGHT.** A
   reasonable guess from the field name, and wrong — `left` and `right` are
   invalid and fall back to CENTER. Horizontal alignment is the separate
   `halign` field.
2. **`Enum.TryParse` accepts numbers.** `event1ConditionAction=1` means
   DISABLE and `=2` means HIDE, and .NET does not range-check: `99` yields an
   enum that prints as "99". It also ORs comma-separated names even though the
   enum is not `[Flags]`. Two fuzz cases in 3,000 hit this, and real content
   plausibly would.
3. **`maxHero` timing.** The C# only takes it from the game context *inside*
   `Populate`, after the format check, so an invalid quest keeps the declared
   default of 5.

**Deviations, all cases where the C# aborts** (see
`webapp/docs/quest-port-deviations.md`): `Application.Quit()` on a Tile with no
side, on a duplicate section, and on an unreadable ini; and
`IndexOutOfRangeException` on a malformed `VarOperation`, which currently takes
down the whole quest load rather than the one bad line.

**Harness note.** `QuestData`'s dispatch and `Quest.Populate` are private and
the constructor reads files, so the harness builds instances with
`GetUninitializedObject` and drives them by reflection. That skips static
initializers too, which produced two convincing false failures — `currentFormat`
defaulted to 0 so every format check failed, and the `valid` field stayed false
because the constructor, not `Populate`, assigns it. Both were harness bugs
that looked exactly like port bugs until traced.

**Scope.** File loading, editor-only constructors and the download-manager
fields are left to T-011, T-019 and T-013 respectively.
