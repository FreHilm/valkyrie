## Goal

Port the content layer: `ContentData.cs` (808 lines), `ContentPack.cs`, `ContentTypes.cs`
(666 lines), `ContentLoader.cs`, `ManifestManager.cs` and `FormatVersions.cs`.

19 of the 22 files in `unity/Assets/Scripts/Content` barely touch Unity, so this is the
largest block of directly translatable code in the project.

## Acceptance Criteria

- [x] All content types ported: heroes, monsters, items, tiles, tokens, perils, activations, classes, skills, puzzles
- [x] Content pack discovery, dependency resolution and override precedence behave identically
- [x] Format version checks ported, including the compatibility rules in `FormatVersions.cs`
- [x] Cases from `ContentDataTests.cs` and `ContentTypesTests.cs` (1798 lines) pass
- [x] Texture path resolution (`ContentData.cs:520`) delegates to the abstraction from T-001
      rather than probing the filesystem directly
- [x] Loading a real D2E and a real MoM content set produces the same in-memory model as Unity

## Notes

`ContentData` currently mixes the data model with Unity texture loading (`Texture2D`, `Sprite`,
DDS unpacking at lines 600-660). Split those: the model stays engine-free in the core package,
and image decoding moves behind an interface the UI package implements. This split is what keeps
the core package testable in Node.

## Progress

### 2026-08-25

Ported and verified. 76 new tests (306 total), 97.85% statement coverage.

**Differential harness** (`tools/differential/content`) compiles the real
`ContentTypes.cs`, `ContentData.cs`, `ContentLoader.cs` and `ContentPack.cs`
unmodified against shims, and reaches their private members **by reflection**
rather than editing them to be testable. The dumper walks public fields and
properties reflectively instead of listing them by hand, so a field the port
forgot shows up as a difference rather than being silently skipped.

| Corpus | Cases | Real divergences |
| --- | ---: | ---: |
| Hand-written edge cases | 74 | 0 |
| Fuzz | 8,000 | 0 |
| **All 62 shipped content packs, ~5,788 sections** | 124 | 0 |

Four rounds of real bugs found and fixed, none of which the hand-written tests
would have caught:

1. **Two float parsers that disagree.** `ContentTypes.cs` uses the explicit
   `float.TryParse(s, NumberStyles.Float, InvariantCulture, out v)` overload,
   which does **not** include `AllowThousands`. So `health=0,5` parses as 0
   here, while the bare overload used in `Audio.cs` reads the same text as 5.
   Added `parseFloatStrict` alongside `parseFloatInvariant`.
2. **Two path-building conventions.** The C# mixes `Path.Combine(a, b)` (used
   by the image loop) with `a + Path.DirectorySeparatorChar + b` (used by the
   pack fields, `imageplace` and `file`). The difference is observable: a pack
   with no `image` key stores a path ending in a slash. Collapsing them into
   one helper produced six differences.
3. **`icon` is null, not `""`,** when a pack declares none — the C# field is
   never assigned.
4. **The harness itself needed a real filesystem.** Running with no texture
   resolver made every image `""` and dropped every token, which surfaced as 22
   differences until the TS side got `makeTextureResolver(existsSync)`.

**Preserved bug worth fixing in the Unity build.** `TokenData.init` guards the
*width* parse with `ContainsKey("height")`:

```csharp
if (content.ContainsKey("height")) { int.TryParse(content["height"], out height); }
if (content.ContainsKey("height")) { int.TryParse(content["width"],  out width);  }
```

A token declaring `height` but not `width` throws `KeyNotFoundException` and
aborts the pack load; one declaring `width` but not `height` silently ignores
it. No shipped content hits either case — every token section has both or
neither — but community content could.

**Scope.** Pack discovery, archive extraction, texture decoding and the path
helpers are filesystem/renderer work left to T-011/T-012/T-013/T-001, as the
task notes anticipated. `PerilData` is deferred to T-008 because it extends
`QuestData.Event`; `ContentLoader` therefore takes its loader list as a
parameter rather than holding it in a static field, so adding `PerilDataLoader`
later needs no edit to the loader itself.

**API note.** The C#'s `Get<T>` / `Values<T>` / `AddContent<T>` rely on reified
generics, so the port passes the content class as an explicit type token:
`cd.get(HeroData, 'HeroFoo')`. Same type safety, same bucket-per-type keying.

**Test-quality note, in contrast to T-005 and T-006:** `ContentTypesTests.cs`
is a *good* suite — 90 of its 114 cases construct the real types rather than
simulating them. The migration was close to one-for-one.
