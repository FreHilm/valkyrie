## Goal

Build the virtual filesystem the ported code sits on. The current codebase assumes a real
filesystem throughout: 187 `Path.` calls, 68 `Directory.` calls and 66 `File.` calls across
39 files.

## Acceptance Criteria

- [x] A filesystem interface covering what the ported code needs: read, write, list, delete, exists, recursive walk
- [x] OPFS-backed implementation for bulk content (imported assets, content packs)
- [x] A Node-backed implementation of the same interface, so core tests run without a browser
- [x] Path handling normalised — the current code mixes separators and relies on
      `Path.DirectorySeparatorChar` in places
- [x] Quota handling: detect available space, fail clearly when full, and surface it to the user
- [x] Temp directory semantics preserved (`ContentData.TempValkyriePath`, `ExtractManager.CleanTemp`)
- [ ] Concurrent access from workers behaves correctly

## Notes

OPFS is the right target for the imported FFG content: it is origin-private, handles large
binaries, and offers synchronous access inside workers, which matters for the importer.
IndexedDB is the better fit for small structured records (config, save index).

Storage volume is the risk. A full D2E plus MoM import is hundreds of MB. Browser eviction under
storage pressure would destroy a user's import, so `navigator.storage.persist()` and a clear
recovery path both need to be in scope rather than assumed.

## Progress

### 2026-08-25

Built as a new `@valkyrie/platform` package. 76 tests, 96.34% statement
coverage on the package (724 tests overall).

**Three implementations behind one interface**, all run through the same
suite so a behaviour that only holds in memory cannot pass unnoticed:

- `MemoryFileSystem` — core tests, and anywhere a real one is unavailable
- `NodeFileSystem` — tooling and the differential harnesses
- `OpfsFileSystem` — the browser

The interface is **async**, because OPFS is. The 66 `File.` and 68
`Directory.` call sites in the C# become awaited ones as each subsystem is
ported.

**OPFS is tested.** It only exists in a browser, so without a fake it would
have shipped untested — the one implementation that actually holds the user's
imported content. `test/fakeOpfs.ts` models the handle tree, quota rejection
and `persist()`, and the shared suite runs against it.

**Two real bugs found by the tests:**

1. **The Node sandbox did not contain anything.** `real()` used `combine(root,
   path)`, and `combine` follows `Path.Combine` where a rooted second segment
   *replaces* the first — so `/a.txt` resolved to the real filesystem root.
   Every write in the suite was landing outside the temp directory.
2. **`..` still escaped** after the first fix, because `resolve("../../x")`
   keeps the leading `..` for a relative path. Paths are now resolved as if
   rooted, so a caller cannot climb out.

**The CRLF decision from T-006 is implemented here.** `readLines` splits on
`\r\n | \r | \n` alike. The Unity reader splits on `\r` only when the file
contains any `\r`, so a single `\n`-only line ending silently merges a key
into the previous value — the trap `.agent/rules/text-localization.md` warns
about. Every shipped localization file parses identically under the new rule
(confirmed by the i18n differential), and the failure mode disappears.

**Storage pressure is treated as a first-class failure.** `StorageFullError`
names the path and the usage/quota numbers so the UI can explain it;
`requestPersistence()` asks the browser not to evict, which matters because a
multi-hundred-megabyte import lost to storage pressure is indistinguishable
from the app breaking.

`StoragePaths` reproduces the layout `ContentData`'s static path helpers
describe, with the roots supplied rather than read from
`Application.persistentDataPath` / `Game.AppData()`.

**Not done:** concurrent access from workers. The OPFS implementation uses the
async handle API, which is safe to call from a worker, but nothing yet
coordinates two writers on the same file. That belongs with T-014, which is
the first thing to actually run in a worker.
