## Goal

Port save/load and user configuration: `SaveManager.cs`, `GameStateManager.cs`, the runtime
state half of `Quest.cs` (2817 lines), `QuestLog.cs` and `StatsManager.cs`.

## Acceptance Criteria

- [ ] Save and load of in-progress quests, including the undo history the current implementation keeps
- [x] Cases from `SaveLoadTests.cs` and `QuestLogTests.cs` pass
- [ ] Save format compatibility with the Unity build settled and implemented per the T-003 decision
- [x] Save export and import as files, so users can move saves between devices — this replaces
      what the desktop filesystem used to provide for free
- [x] User config persisted (`ConfigFile`), including per-game settings
- [ ] Autosave behaviour preserved
- [x] Save thumbnails preserved (`EXTRACT_SAVE_INI_PIC` handles `image.png` today)

## Notes

Save compatibility is a real decision, not a detail. If web and Unity saves interoperate, users
can move between builds during the transition and the port can ship incrementally. If they do
not, the web port is effectively a separate product from day one. T-003 should have settled this;
if it did not, escalate rather than picking silently.

Note the known defect carried in `Quest.cs:2699`: random hero selection is not preserved across
save/load or undo. Decide whether the port fixes it or reproduces it — fixing it may itself break
save compatibility.

## Progress

**2026-08-25 — done for the save envelope; two criteria are partly met and one
carries an assumption. All three are called out below rather than glossed.**

Ported to `packages/core/src/quest/QuestLog.ts` (`QuestLog` + `LogEntry`),
`packages/platform/src/save.ts` (the save envelope) and
`packages/platform/src/configStore.ts` (the config I/O T-005 deferred until a
filesystem existed). 105 new tests.

**All 59 C# cases migrated, by name**: `QuestLogTests` 25/25 and `SaveLoadTests`
34/34 in the conformance ledger.

**Honest note on assurance.** This is the first port with **no differential
harness**, and the docs lead with that. `SaveManager.cs` cannot be compiled
outside Unity — it reaches `Game.Get()`, `Screen`, `Texture2D` and the UI stack
from inside its save and load methods, and the logic is inline rather than in
extractable functions. `LogEntry`/`QuestLog` are fully covered by the migrated
suite; the envelope handling is transcribed and covered by new tests but never
checked by running the original. It is the weakest link in the port so far and
should be re-checked against real `.vSave` files when any are available.

**Superseded 2026-08-25: saves no longer interoperate with the Unity build.**
The decision below was made under the conservative default; it has since been
taken the other way. The envelope this task built is unchanged — same zip
layout, same four slots — but it is now free to diverge, and the runtime
defects it documented are to be fixed rather than reproduced.

**The save-format decision was NOT mine to make, so it is flagged not buried.**
The task says T-003 should have settled interoperability with the Unity build
and to escalate rather than pick silently. T-003 is not written. The port
**preserves the existing format** — same zip layout, same keys, same four slots
— because that is the conservative choice, costs nothing, and keeps
interoperability open. One thing does already diverge: `LogEntry.ToString` uses
`Environment.NewLine`, so the port writes `\n` where a Windows Unity build
writes `\r\n`. Parsers on both sides tolerate either, but a byte comparison
will show it. **This still needs your decision.**

**A platform bug in the C# suite itself:** `QuestLogTests.cs` asserts
`"quest5=Test message\r\n"` literally, so those cases only pass on Windows.

**Defects found and fixed rather than reproduced:**

- `DateTime.Parse` on a save's `time` **throws** on a malformed value, and the
  catch reports "unable to open save file" — discarding an otherwise perfectly
  good save. The port returns null and keeps the save valid.
- The legacy pack expansion uses `if`/`if`/`if`/`else`, so the `else` binds only
  to the `MoM1E` test: a save naming `FA` loads `FAI`/`FAM`/`FAT` **and** then
  `LoadContentID("FA")`, which is not a pack that exists.
- `ConfigFile.Save` catches everything and logs a warning, silently losing the
  user's settings. In a browser a storage quota is a normal condition, so the
  port surfaces `StorageFullError`.
- Both version gates existed as two separate copies (metadata read and load
  path) that could drift; extracted into one `checkSaveVersion`.

**Export and import are new, not ported** — there was nothing to port. On the
desktop a user could copy `saveAuto.vSave` out of the app data directory; the
origin-private filesystem is not reachable that way. `importSave` version-gates
the archive *before writing*, so a wrong or hostile file cannot destroy the
save already in that slot; there is a test for exactly that, and for filename
sanitising (`../../etc/passwd` becomes `.._.._etc_passwd-1.vSave`).

**Not met — the runtime quest state, and with it the undo history and
autosave.** `save.ini` is written by `Quest.ToString()`, which serialises the
live `Quest` object: board items, monsters, heroes, shops, undo. That object
depends on `Monster`, `Hero`, `BoardComponent` and the event engine, none of
which are ported. This task delivers the envelope — read, write, list, gate,
export, import, and the log inside it. The undo history and autosave scheduling
ride on the same serialisation and belong with the quest runtime.

The known defect at `Quest.cs:2699` (random hero selection not preserved across
save/load or undo) is untouched, and deliberately: fixing it changes what
`save.ini` contains, which is the same interoperability question as above.

Deviations in `webapp/docs/save-port-deviations.md`. Full suite: 938 tests,
lint/format/typecheck clean.

- 2026-08-28: Closed with four criteria unchecked, and they are still unmet. What
