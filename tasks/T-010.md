## Goal

Bring the existing NUnit suite across as the conformance suite for the port. There are 893
`[Test]`/`[TestCase]` cases across 25 files and 14.2k LOC in `unity/Assets/UnitTests/Editor`,
covering exactly the layers being ported: parsing, content loading, save/load, var expressions
and localization.

This is the single highest-value de-risking step in the project. If the TypeScript core passes
the same tests as the C# core, the riskiest 13k LOC is proven before any UI work begins.

## Acceptance Criteria

- [x] All 893 cases either ported, or explicitly marked out-of-scope with a recorded reason
- [x] Ported tests run in CI on every PR
- [x] Coverage reported and compared against the Unity suite's reach
- [x] Any behavioural divergence found during porting is recorded as a decision, not silently accepted
- [ ] `ZipSlipTests.cs` in particular is ported and passing — it guards a real security property (see T-012)
- [x] A scenario corpus test loads published community quests end to end

## Notes

Where the C# test asserts something surprising, the test is usually right and encodes a real
compatibility requirement. Treat a failing ported test as a bug in the port until proven otherwise.

`TestHelpers/TestGameProvider.cs` exists because the Unity code reaches through the `Game.game`
singleton (509 `Game.Get()` calls across 99 of 145 files). The ported core should not need an
equivalent — if it does, the dependency boundary from T-004 has leaked.

## Progress

### 2026-08-25

Delivered as a **self-checking ledger** rather than a one-time migration
report: `webapp/tools/conformance/ledger.mjs` enumerates every
`[Test]`/`[TestCase]` in the Unity suite, records its disposition, and fails
if a file has none — so a suite added upstream cannot go unnoticed. Wired into
CI. Written up in `webapp/docs/conformance-ledger.md`.

All 893 cases accounted for:

| | cases |
| --- | ---: |
| ported (subsystem is ported; covered by the TS suite and the differential harness) | 664 |
| deferred (needs a subsystem not ported yet, task named) | 228 |
| dismissed (`DummyTest` asserts `true == true`) | 1 |

648 TypeScript tests, 97.49% statement coverage.

**The ledger verifies rather than asserts.** It name-matches each C# case
against a TypeScript test of the same name and reports the rate. That
immediately exposed my own overstatement: the first run showed 27% matched,
because several suites had been migrated as behaviour groups. Adding
name-for-name tests for the pure-function suites (`conformance.test.ts`, 160
cases) took it to **336/664 (51%)**. The remainder — chiefly
`QuestComponentTests` (179) and `ContentTypesTests` (93) — is behaviour-grouped
by design, and the doc says so explicitly rather than quietly counting it as
migrated.

**132 of the 893 C# cases are `simulated`** — they re-implement the algorithm
inline and assert against their own copy, so they pass whether or not the
production code works. `DictionaryI18nTests` (70 of 72), `ConfigFileTests`
(all 18) and part of `LocalizationReadTests`. On migration they were
re-pointed at the real implementation. Worth knowing before treating "893
tests" as 893 tests of the shipped code.

**What actually establishes equivalence** is the differential harness, not the
migrated cases: five harnesses, fourteen corpora, ~90,000 cases including all
236 shipped `.ini` files, all 20 localization files, all 62 content packs and
2,744 sections from 12 real downloaded scenarios. Zero real divergences.

Every bug found in the port came from that, not from the migrated tests: the
`AllowThousands` cases, `Enum.TryParse` accepting numbers, the short-circuit in
nested conditions, float32 storage, and the int32 overflow in the Android
version code.

**Also ported here** (they had no owning task): `VersionManager`'s comparison
logic and `SetVersion`'s version-code generator, plus a fuzz differential for
both. That found a real bug — the C# accumulates the version code into an
`int`, so `300.0.0` overflows to `-1294967296`, and a negative value then
passes the "exceeds android limit" check and is returned.
