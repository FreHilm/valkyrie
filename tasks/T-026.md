## Goal

Write the missing half of save/load: a serialiser for live quest state, the
undo stack it also feeds, and the screens that reach both.

## Acceptance Criteria

- [x] A `Quest.ToString`-equivalent serialiser that round-trips live quest state
- [x] Saving an in-progress quest to a slot, and loading it back into a playable session
- [x] The undo stack: `Quest.Save` pushes, `Quest.Undo` restores, and `cancelable` events push before they run
- [x] Autosave preserved
- [ ] A save-select screen (`SaveSelectScreen.cs`)
- [x] Save-format compatibility with the Unity build settled per the T-003 decision, and honoured
- [x] Round-trip verified in a browser: save mid-scenario, reload the page, resume where it left off

## Notes

Carries the four unmet acceptance criteria of T-015, which was closed with them
unchecked. What T-015 *did* land is real and should not be redone:
`packages/platform/src/save.ts` reads metadata, lists, imports, exports and
deletes saves, and user config persists. What is missing is that nothing can
**write** one — there is no quest-state serialiser anywhere in the port — and
no screen reaches any of it.

`cancelable` is parsed onto `QuestEvent` and never read; it exists precisely to
mark the events that push an undo point.

Depends on nothing new, but T-030 (the in-quest menu) cannot land without it.

## Progress

- 2026-08-28: Found while auditing the play loop against the C#. Confirmed no
  serialiser exists and no app or UI code calls `save.ts`.

- 2026-08-28: Serialiser and undo landed; slots, autosave and the screen still
  to come.

  The format question was already answered and I nearly re-opened it.
  `save-port-deviations.md` records an assumption to preserve the C# format,
  written when T-003 had not been drafted — but `adr/0001` has a "Settled
  2026-08-25" section stating plainly that **saves do not interoperate with the
  Unity build**, and the two open questions there are the browser matrix and
  the renderer, not this. So the port records what it models rather than every
  key the C# emits: no camera position, hero classes or shops. The shape stays
  the C#'s because our own reader already parses it.

  Two things about the undo were not what the task text assumed:

  - `cancelable` is a property of the *type*, not an ini key. Doors, tokens and
    UI elements are cancelable "because you can select then cancel"
    (`QuestData.cs:351`), and the port already set it on all three — it was
    only ever unread.
  - An event's operations run when it fires, inside `TriggerEvent`, not when
    its button is pressed. The point recorded on a token's button therefore
    protects what the button leads to, not the token's own effect.

  The round-trip tests earned their keep immediately: `[EventList]` serialised
  and never restored, which is worse than doing neither because it looks like
  it worked.

- 2026-08-28: Autosave and resume are wired and verified in Chrome. Only the
  save-select screen is left.

  The `save` hook already existed on the session and the round controller
  already called it at both round boundaries — nothing had ever supplied one.
  The quest-start autosave (`Quest.cs:770`) was missing and is added, so a
  player who closes the tab during the first round still has a game.

  Three things the browser found that the tests could not:

  - `__VALKYRIE_VERSION__` is a display string and is "dev" in a dev build. The
    `valkyrie=` key is a compatibility gate that `checkSaveVersion` parses as a
    version, so a save stamped "dev" was rejected as unsupported. Saves now
    carry `SAVE_VERSION`, tracking the Unity project's `bundleVersion`.
  - Quest files have to go into the archive under `quest/`, which is where
    `resolveQuestPath` points a load. Stored flat, the load looked for
    `Load/quest/quest.ini` and found nothing.
  - Resuming must not call `setUpParty` or `session.start()`: the party was
    chosen a session ago and `EventStart` has already run, so doing it again
    deals the items out twice and replays the opening over a built board.
