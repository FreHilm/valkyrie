## Goal

Decide how the FFG asset extraction pipeline runs without Unity. `libraries/FFGAppImport`
is 48k LOC — larger than the entire Unity script folder — and splits into
18.5k of AssetStudio (Unity asset bundle reader), 26.7k of vendored Ogg Vorbis encoder,
and 2.7k of Valkyrie-specific glue (`FetchContent.cs`, `ExtractDataTool.cs`, `FSBExport.cs`,
`AppFinder.cs`).

This is the single largest obstacle to a browser-only port, and the main argument for
introducing Node.

## Acceptance Criteria

- [ ] Prototype each option far enough to compare honestly:
  - [ ] A: compile the existing C# to WASM (.NET WASM / Blazor) and run it in a worker
  - [ ] B: rewrite the 2.7k glue in TypeScript, keep AssetStudio's bundle reading as a WASM module
  - [ ] C: keep a Node CLI importer that emits a web-ready content bundle
  - [ ] D: keep a small desktop importer, browser consumes its output
- [ ] Each option scored on: bundle size, import wall-clock, mobile viability, maintenance burden
- [ ] Confirm whether the 26.7k ogg encoder is needed at all, or whether `OggVorbisHeader.cs`
      header reconstruction over raw FSB vorbis is sufficient (Web Audio may decode it directly)
- [ ] Recommendation written up, feeding T-003 and T-014

## Notes

`ImportManager.ImportZip` already accepts a zip of raw FFG app data, so a browser file-input
path exists conceptually. But the zip contents still go through AssetStudio, so this does not
avoid the problem.

On Android the browser cannot reach another app's OBB or data directory at all, so the
auto-detect path (`AppFinder.cs`, `RtLFinder.cs`, `MoMFinder.cs`, `Registry.cs`) has no web
equivalent. Web users will always supply a file explicitly.

## Progress

**2026-08-25 — done. Option C in spirit: a targeted TypeScript reader, not a
port of AssetStudio and not WASM.**

The 48k LOC breaks down very differently once measured rather than counted:

- **26.7k of vendored Ogg Vorbis encoder is not needed at all.** `FSBExport`
  never encodes audio — FSB5 stores Vorbis packets with their headers stripped,
  and the encoder is used only to build two headers and frame Ogg pages.
  Replaced by ~200 lines in T-020, verified byte-identical across 4,180 cases.
- **18.5k of AssetStudio reads every Unity class there has ever been.** The
  import needs three: `Texture2D`, `AudioClip`, `TextAsset`. A targeted
  `SerializedFile` reader is ~560 lines.

**Verified against the real thing**: `tools/differential/unity` runs the actual
AssetStudio over a licensed MoM 2.1.6 install and compares every object.
**936 of 936 match byte-for-byte** — 733 textures, 174 audio clips, 29 text
assets.

Mutation-tested; a wrong stream-offset width broke 720 of 936 objects. One
mutation was *not* caught — an alignment after `m_StreamingMipmaps`, because
every texture in this install already sits on a boundary — and that gap is now
pinned by synthetic tests.

**WASM was not prototyped.** The targeted reader landed and was verified, so
building the alternative to compare would have been work for a decision already
made on evidence. Flagging that the comparison in the acceptance criteria was
not performed, rather than implying it was.

**A finding that matters more than the choice**: MoM 2.1.6 downloads its game
content on first run and caches it outside the install
(`~/Library/Caches/com.fantasyflightgames.mom`, 413 MB of UnityFS
AssetBundles). `FetchContent` looks only inside the install and cannot read
bundles, so **the shipped Unity importer is already broken against current
builds too**. The `Localization_*` text is right there in the bundles, under
exactly the filenames the importer expects; recovering it needs the cache path
and an uncompressed `UnityFS` reader, not a type-tree database.

*(Corrected the same day: an earlier note here said the text had moved into
MonoBehaviour and needed a type-tree database. The MonoBehaviour objects hold
key names only — the strings were never in the install.)*

Details in `webapp/docs/ffg-import.md`.
