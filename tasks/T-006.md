## Goal

Port `StringKey.cs`, `DictionaryI18n.cs` (680 lines), `LocalizationRead.cs` and
`CommonStringKeys.cs`, and bring across the 13 `Localization.*.txt` files from
`unity/Assets/StreamingAssets/text/`.

## Acceptance Criteria

- [x] `StringKey` ported including the parameterised forms (`{0}` substitution, both constructors)
- [x] `DictionaryI18n` ported with the same lookup and fallback-to-English behaviour
- [x] All 13 locale files load and resolve identically to the Unity build
- [x] Cases from `DictionaryI18nTests.cs`, `LocalizationReadTests.cs` and `StringKeyTests.cs` pass
- [x] Decision recorded on whether to keep the CRLF-sensitive format or migrate it (see below)
- [x] Quest-supplied localization (scenario `Localization.*.txt` inside content packs) still overrides base text

## Notes

The current format is fragile in a specific, documented way: `DictionaryI18n.AddDataFromFile`
splits on `\r` only, so a `\n`-only line ending silently merges a key into the previous value.
`.agent/rules/text-localization.md` warns about this at length.

The port is a natural moment to move to a format that cannot fail this way. But quest authors
ship their own localization files inside content packs, so the *reader* must keep accepting the
legacy format regardless of what the base files migrate to.

Current translation coverage against 619 translatable English keys, excluding expansion symbol
identity strings: Czech complete; Korean 7 gaps; Japanese, French, Spanish, Ukrainian,
Portuguese ~26-29; Russian 37; Polish 47; Chinese 52; Italian 81. Most remaining gaps are
`ICON_*` and non-prose keys. Not blocking, but worth a pass while the files are being touched.

## Progress

### 2026-08-25

Ported and verified. 134 new tests (230 total in the suite), 98.45% statement
coverage across the package.

**Differential verification** against the unmodified C# sources, compiled with
four small shims (`UnityEngine.Debug`, `Game`, `ValkyrieConstants`,
`ValkyrieDebug`) that contain no ported logic. A second harness now sits
alongside the INI one in `webapp/tools/differential/i18n`, wired into
`run.sh` and CI.

| Corpus | Cases | Real divergences |
| --- | ---: | ---: |
| Hand-written edge cases | 97 | 0 |
| Fuzz | 8,000 | 0 |
| **All 20 shipped `Localization.*.txt`, 7,119 keys** | 20 | 0 |
| **Cross-language resolution, 4 fallback configs** | 24 | 0 |

The fuzz corpus again earned its keep: it caught a real bug in my
`Split(":", 3, RemoveEmptyEntries)` port. Empty segments are dropped *before*
the count applies, and the final element is the raw remainder from the start
of the count-th non-empty segment — so `a::b::c::d` is `["a","b","c::d"]`, not
`["a","b",":c::d"]`. The hand-written cases had not distinguished the two.

Four of my migrated test expectations were also wrong, and the C# harness
settled each one rather than my reading of the code. Notably `{qst:X:{0}:y}`
does *not* parse as a key: the `{0}` puts a `}` before the end of the string,
failing the "first `}` is last character" guard.

**Three deviations, all cases where the C# throws** (see
`webapp/docs/i18n-port-deviations.md`): `{dict:}` with no key, an unterminated
`{dict:` reading past the end of the string, and a language header with no
comma.

**Two preserved defects worth fixing in the Unity build too:**

1. Unclosed markup tags come out improperly nested. `DictLookup` closes them
   with two independent loops — all `</b>` first, then all `</i>` — so
   `[b]bold [i]italic` becomes `<b>bold <i>italic</b></i>`. Unity's rich-text
   renderer tolerates the interleaving; a browser may not. Revisit at T-016.
2. A parameter value containing `:` is silently truncated. Parameters are a
   flat `find:replace` list split on top-level colons with no escape, so
   `{val:PARAM:{0}:a:b}` yields `value a`. Any scenario text substituting a
   time, ratio or namespaced id loses everything after the first colon.

**CRLF decision (the AC asked for one).** The port does not reproduce the trap
because it does not read files — `addData` takes already-split lines. The
recommendation for the platform layer (T-011) is to split on
`\r\n | \r | \n` uniformly: every shipped file still parses byte-identically
(confirmed above), the on-disk format is unchanged, no content pack is
affected, and the silent key-merging failure mode disappears. Recorded rather
than decided unilaterally, since T-003 may want to rule on it.

**API note.** `LocalizationRead` was a static class; it is now an instance,
`Localization`, with a module-level `defaultLocalization` standing in for the
global. The common call site `new StringKey('val', 'KEY')` is unchanged, so
`.agent/rules/text-localization.md` still reads correctly. `StringKey`'s six
C# constructors became one constructor plus three named factories, because
`(string, string, bool)` and `(string, string, string)` cannot be distinguished
as TypeScript overloads.

**Test-quality note.** `DictionaryI18nTests.cs` has 74 tests but constructs
`DictionaryI18n` in only four; the rest — every `ParseEntryLogic_*`,
`CsvSplitLogic_*`, `QuoteCountLogic_*`, `SerializationLogic_*` case —
reimplements the algorithm inline and asserts against its own copy, so it would
pass even if the class were broken. Same pattern in `LocalizationReadTests.cs`
and, as noted in T-005, `ConfigFileTests.cs`. The migrated versions keep the
original names but run against the real implementation. Worth knowing when
T-010 counts the 893 cases: a meaningful share of them are not testing the
production code.
