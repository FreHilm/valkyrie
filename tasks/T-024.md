## Goal

Pass an `onPuzzle` renderer to `playScreen` so a puzzle event actually draws
something. `packages/ui/src/screens/puzzles.ts` holds all four puzzle screens
and they are already tested; nothing reaches them from a real quest.

## Acceptance Criteria

- [x] `main.ts` supplies `onPuzzle` to `playScreen`, rendering into the overlay it is handed
- [x] All four classes reachable in play: `code`, `image`, `slide`, `tower`
- [x] Solving one calls `finishPuzzle` and the quest continues to the event's buttons
- [x] Giving up calls `closePuzzle` and returns to the board with progress intact
- [x] `puzzlealtlevel` and the `skill` line are honoured, as `PuzzleCodeWindow` honours them
- [x] Verified in a browser: all four classes open, a code puzzle solves, and the quest goes on

## Notes

This is the hard blocker on finishing any scenario. `playScreen` already builds
the `chrome` object and calls `options.onPuzzle?.(...)` — with nothing passed,
the call is a no-op and the branch returns having cleared the overlay, so the
player is left on a board with no dialog and no way forward.

Every MoM scenario in the library contains puzzle components:

| Scenario | Puzzle sections |
| --- | --- |
| MoM__TheFallofHouseLynch | 5 |
| MoM__TheTruth | 5 |
| MoM__2230hAtTheBirdsPetShop | 2 |
| MoM__InPlacesUnseen | 2 |
| MoM__TheRobberyOfTheKadakianIdol | 2 |
| MoM__Demo | 1 |
| MoM__ExoticMaterial | 1 |

`EventManager.cs:309` is the C# side: a `QuestData.Puzzle` event opens the
window for its class and returns, and the event's buttons only appear once it
is solved.

## Progress

- 2026-08-28: Found while auditing the play loop against the C#. The screens
  exist and pass their own tests; only the wiring from `main.ts` is missing.

- 2026-08-28: Built `packages/app/src/puzzleView.ts`, the bridge between the
  session's puzzle state and the four screens, and passed it to `playScreen`
  as `onPuzzle`. Two supporting changes in core:

  - `PuzzleSlide.canMove` split out of `moveBlock`, with `destinations(index)`
    over it. The C# only asks whether a move is legal *while making* it, inside
    `MoveBlock`; a screen that offers the squares rather than accepting a drag
    has to ask first, so the rules now live in one place and `moveBlock`
    applies them.
  - `PuzzleTower.move` now counts the move. The C# counts in
    `PuzzleTowerWindow.cs:239` rather than in the model — as its slide and
    image counterparts also do — but this port already counts slide and image
    in the model, so the tally survives a save without the screen keeping it.
    Tower was the one left out, and its counter never moved.

  Eight tests over the bridge; five mutations checked, four bit. The fifth
  showed a conditional in the adapter was dead — the screens' shared chrome
  already picks between "Finish" and "Give up" from `solved` — so that was
  removed rather than tested around.

- 2026-08-28: A second gap surfaced while verifying: a slide puzzle drew itself
  as an ordinary dialog, because `slideLayouts` was declared on the session
  options and never supplied. A slide puzzle is chosen from a shipped set
  rather than generated, so `PuzzleSlide.generate` returned null for every
  difficulty. The 35 layouts from `Assets/Resources/slidepuzzles.txt` — 8 KB of
  Valkyrie's own data, already in this repository — are now embedded as
  `slidePuzzles.ts` and passed from `startQuest`.

  Verified in Chrome against a scratch scenario that opens each class from its
  own button: code, slide, tower and image all draw, a code puzzle solved with
  `1 2 3` reports "3 right place, 0 right symbol" and then "Finish" carries the
  quest on to the next event, and "Give up" returns to the board. The fixture
  is kept in this session's scratchpad for T-032 rather than left in the quest
  library.
