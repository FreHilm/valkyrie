## Goal

Stand up the release pipeline for the web build, replacing what
`.github/workflows/buildAndOptionalRelease.yml` and `workflowScripts/build.ps1` do for the
Unity build.

## Acceptance Criteria

- [x] Build, test and deploy on push, with preview builds for pull requests
- [x] Versioning carried over from the existing `version.txt` / `SetVersion` scheme so the
      in-app version display keeps working
- [x] Static hosting configured — GitHub Pages is the obvious fit given the site already lives there
- [x] Bundle size tracked and budgeted, failing the build on regression
- [x] CodeQL or equivalent security scanning kept in place, matching the current
      `CodeAndSecurityValidation.yml`
- [x] Rollback path that does not require a rebuild
- [x] Decision recorded on whether the Unity pipeline is retired, and when

## Notes

**Dependency on T-021 removed on 2026-08-25.** The PWA packaging shapes what
the site contains, not how it is built, versioned or published. Blocking the
pipeline on it would have left the pipeline unbuilt until late, when it is most
useful early. T-021 is unchanged and still todo.


The web pipeline is substantially simpler than the current one: no Unity license activation, no
per-platform runners, no Android signing, no 40-minute build. That removes several of the
fragilities visible in the existing setup, including the licensing errors captured in the
committed `compile-check.log`.

While touching CI, worth also removing the committed build logs (`compile-check.log`,
`compile-results.log`, `unity/Logs/Packages-Update.log`) and adding the standard Unity entries
to `.gitignore` — unrelated to the port, but this is the task that will be looking at it.

## Progress

**2026-08-25 — done, with the deploy step deliberately inert and one decision
left to you.**

Added `.github/workflows/webRelease.yml`, `webapp/tools/size/check.mjs`,
`webapp/tools/version/print.mjs`, `parseVersionFile` in core, and
`webapp/docs/release-pipeline.md`.

**The deploy step publishes nothing today, and says so.** There is no
`packages/app` until T-016. The workflow detects that and emits a notice rather
than failing, so the pipeline is exercised on every push and starts publishing
the day the app package appears. A green run does not mean a site went live —
worth being explicit about rather than letting the checkbox imply otherwise.

**A real hole found in the existing CI.** `webPort.yml` failed builds by
grepping for `real divergences: [1-9]`. The three harnesses added since
(`multimedia`, `remote`, `ogg`) print the count the other way round — `0 real
divergences` — so **a divergence in any of them would not have failed the
build**. On top of that, `run.sh` was piped into `tee` without `pipefail`, so
its non-zero exit was swallowed as well. Both fixed, the patterns tested
against real output and three synthetic failure shapes, plus a check that the
run actually reached the last harness rather than dying halfway.

**Versioning verified by execution**, not transcription: the real `SetVersion`
was compiled and run against a copy of the repo across four `version.txt`
shapes, and the port agrees on every one, including dropping an unrecognised
channel. (The committed `ProjectSettings.asset` says `3.0.4` against a
`version.txt` of `3.28` — that is just stale checked-in state, since
`SetVersion` runs in the build.)

**Bundle budget**: gzipped size per package, failing past 5% growth, budget
committed so an intended increase shows up in review. Core 51.2 kB, platform
27.7 kB.

**Rollback** republishes a previous run's artifact with no rebuild, so what
goes back up is exactly what was serving before rather than a fresh build of an
old commit.

**PRs get a downloadable artifact, not a preview URL.** Publishing a fork's
build to the project's own Pages origin would let any contributor serve
arbitrary content from the origin that holds the app's OPFS data.

**Repo hygiene** the notes asked for: removed `compile-check.log`,
`compile-results.log` and `unity/Logs/Packages-Update.log` — committed Unity
*licensing failure* logs from a local machine, referenced by nothing, leaking
local paths — and added the standard Unity ignores. One trap avoided and
recorded: the usual template's global `*.csproj`/`*.sln` would have silently
excluded all eight differential-harness project files, breaking the
differential suite on a fresh clone while still looking fine locally. Scoped to
`/unity/`.

**Left to you — retiring the Unity pipeline.** The criterion asks for a
recorded decision and the decision is not mine. The web port has no UI yet and
its import path is blocked on licensed files, so retiring the Unity build now
would leave users with nothing that works. Recommendation recorded in the docs:
keep both, revisit once T-016-T-019 land and the import path is verified. It
belongs in the ADR with the browser-matrix and save-format questions.

CodeQL (`CodeAndSecurityValidation.yml`) is untouched and still running; it
covers the C# too, and the Unity build is not retired.

Full suite: 990 tests, lint/format/typecheck clean, size budget green.
