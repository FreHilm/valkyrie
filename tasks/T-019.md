## Goal

Port the quest editor — `unity/Assets/Scripts/QuestEditor`, 9.0k LOC across 23 files, all of
them uGUI-bound. This is the second half of what Valkyrie is: without it the port is a player,
not the scenario builder the project exists to be.

## Acceptance Criteria

- [ ] All editor components ported, including the large ones: `EditorComponentEvent.cs` (1318 lines),
      `EditorComponentCustomMonster.cs` (1039), `EditorComponentSpawn.cs` (682), `EditorComponentUI.cs` (566)
- [ ] Quest creation, opening and saving (`QuestEditSelection.cs`, `QuestEditorData.cs`)
- [ ] Visual board editing: place and move tiles, tokens, doors, monster spawns
- [ ] Event graph editing with next-event chaining
- [ ] Var test editing (`EditorComponentVarTestsUtil.cs`)
- [ ] Custom monster and custom content authoring
- [ ] Quest packaging to `.valkyrie` for publication
- [ ] Audio and image file selection from within the package
- [x] A quest authored in the web editor loads correctly in the Unity build, and vice versa

## Notes

**Decisions taken 2026-08-25 (second round):**

- **Parity, not complement.** The web editor is the eventual replacement for
  the Unity one, so the two known defects are **fixed** rather than inherited:
  open/save inside packages (`QuestEditSelection.cs:40`) and the untranslated
  expansion traits and base monster names
  (`EditorComponentCustomMonster.cs:34`).

**Decisions taken 2026-08-25 (first round):**

- **Preserve each file's existing line endings**, defaulting new files to LF.
  Community quests live in git, and normalising endings would turn a one-line
  edit into a whole-file diff. Checked against the shipped content: it is
  already mixed — 176 LF to 24 CRLF in a 200-file sample — so both are normal
  and both parse. This resolves the "byte-compatible" acceptance criterion:
  the target is *round-trips without spurious diffs*, not byte-identical to a
  Windows Unity build, which a browser cannot determine anyway.
- **Authoring core first**: events with next-event chaining, board editing
  (tiles, tokens, doors, spawns), var tests, and quest open/save/package.
  Custom monsters (`EditorComponentCustomMonster`, 1,039 lines) and custom
  content follow once the core is usable end to end.


Deliberately sequenced after the play loop. The editor is the larger and more intricate UI, and
building it before T-018 has validated the UI foundation risks doing it twice.

Two known issues in the current editor worth deciding on rather than inheriting:
`QuestEditSelection.cs:40` notes open/save in packages is unfinished, and
`EditorComponentCustomMonster.cs:34` notes expansion traits and base monster names are untranslated.

The last acceptance criterion is the important one. If web-authored quests are not byte-compatible
with the Unity build, the community splits across two incompatible tools during the transition.

## Progress

**2026-08-25 — the round-trip criterion is met and verified against real
published scenarios. The editor UI itself is not built; detail below.**

**The last acceptance criterion was the important one**, as the notes say, and
it is now demonstrated rather than argued.
`tools/differential/questwrite` downloads twelve published scenarios and, for
each of their **103 quest files**, parses, writes and re-parses, checking both
that the data survives and that the line ending does.

**103 of 103 round-trip, 0 divergences.**

**Your line-ending decision is vindicated by the data.** Of those 103 files,
**101 are CRLF** — written by the Unity editor on Windows — and 2 are LF.
Normalising would have rewritten every line of almost every published quest,
making review of a one-line change impossible. `rewriteIni` preserves whatever
a file already used and defaults new files to LF.

**A bug the real corpus found:** some quest files contain nothing but the
`; Saved by version: X` marker the Unity editor writes. Serialising them
produced an *empty file*, silently dropping the marker. `rewriteIni` now keeps
the leading comments, and a test pins it.

**A weakness in my own check, found by mutation testing.** The first version
compared the written file's line ending against the original's using the same
`detectNewline` under test — so a writer that always normalised to LF looked
correct, because both sides agreed. The harness now measures the bytes
independently, and the same mutation produces 101 divergences instead of 0.
This is the second time that pattern has appeared, after the stale `dist` in
T-020.

**Not built: the editor UI.** The authoring core you chose — event editing with
next-event chaining, board editing, var tests, open/save/package — is not
implemented. What is done is the *file format* half that everything else
depends on and that decides compatibility, plus the board rendering and hit
testing from T-017 that visual editing will sit on.

The two known defects in the notes are untouched and still worth deciding on:
`QuestEditSelection.cs:40` (open/save in packages unfinished) and
`EditorComponentCustomMonster.cs:34` (expansion traits untranslated).
